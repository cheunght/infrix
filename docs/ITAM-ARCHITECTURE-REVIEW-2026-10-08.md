## 1. 总体判断

当前系统已经具备基础设施资产运营平台的主要界面和基础业务：资产台账、标准型号、自定义字段、使用人流转、数据中心/机房/机柜、维修、备件库存、盘点、折旧、通知、LDAP、2FA、审计和安装维护。它具备继续演进的基础，技术栈本身没有需要推翻的理由。

但功能页面的完整程度高于业务约束和运行保障的完整程度。此次审查复现了安全策略入口不一致、库存数据错误、告警崩溃、备份附件不一致等问题。若用于多个部门共同维护生产主台账，建议先修复这些问题，再扩大使用范围。当前更适合范围受控、有人维护数据质量的试点。

对成熟 ITAM 的差距主要在数据发现和对账、生命周期流程、软件授权合规、合同采购关系、历史事实留存、数据范围权限及运行保障。新增页面本身不能填补这些差距。

以下将实现缺陷、架构风险和产品能力缺口分开记录。P1 表示优先修复的安全、可用性或数据正确性问题；P2 表示需要纳入近期整改的体验、统计及性能问题。优先级是本次审查判断，不是漏洞评级或行业认证。

## 3. Standards 轴：安全、实现与工程结构

### S01 · P1 · 已有 API Token 绕过强制修改密码

证据：[middleware.py:23](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/middleware.py:23)、[auth_security.py:119](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/auth_security.py:119)、[views.py:2764](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/views.py:2764)。

强制改密中间件在 DRF 的 Bearer 认证之前执行。对于只携带 Token 的请求，此时 Django 的 `request.user` 尚未成为 Token 用户，因此校验不会生效。Token 认证检查有效期、撤销和账号启用状态，未检查强制改密标记；管理员密码重置也没有撤销已有 Token。

隔离复现：

```text
must_change_password=True
Session GET /api/v1/assets/ -> 403
旧 PAT GET /api/v1/assets/ -> 200
旧 PAT POST /api/v1/tags/ -> 201
```

影响：密码已被管理员重置、系统要求先改密的账号，仍可用旧 Token 读写原有权限范围内的数据。若重置密码用于处置凭证泄露，原 API 凭证仍有效。

建议：在所有认证方式完成之后统一执行账号安全策略；明确密码重置、强制改密和安全事件对 Token 的撤销规则。回归测试应覆盖 Session、PAT 和 Admin 三类入口。

### S02 · 已撤回 · Admin 登录限流误判

证据：[admin_auth.py:70](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/admin_auth.py:70)。

复查真实 HTTP 入口后确认：`SecureAdminSite.login()` 在调用密码表单前检查 API 共用的账号/IP 锁定，并在认证失败时共用失败计数。

原审查仅直接调用密码表单，未经过实际入口，不能据此推断 Admin 登录可以绕过限流。真实入口复现：5 次 API 密码失败后，Admin 页面显示锁定信息，未建立认证会话。

此次撤回该缺陷并加入 API/Admin 双向锁定回归测试。Admin 强制改密策略缺失仍为独立问题，见 S03。

该项无需重新实现限流。

### S03 · P2 · Admin 不执行强制改密策略

证据：[admin_auth.py:118](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/admin_auth.py:118)、[middleware.py:23](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/middleware.py:23)。

Admin 权限检查只判断账号启用、staff 和已启用的 2FA。强制改密中间件只覆盖 `/api/v1/`；Admin 的密码入口也没有共享 API 的密码过期检查。

隔离复现：`must_change_password=True` 的超级管理员仍通过 `SecureAdminSite.has_permission()`。

现有业务 Admin 为只读，因此本次确认的影响是读取资产及审计信息，不能据此声称它能通过 Admin 修改全部业务。建议统一入口安全策略，并决定 Admin 是否有必要对一般用户开放。

### S04 · P1 · 备份“有效”不保证数据库与附件一致

证据：[backups.py:513](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/backups.py:513)、[backups.py:528](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/backups.py:528)、[models.py:1188](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/models.py:1188)。

数据库 dump 完成后才复制媒体目录。备份锁只协调备份/恢复等维护操作，普通附件删除不参与该锁。如果附件在数据库快照之后、媒体复制之前被删除，快照保留附件记录，但归档缺少文件。

隔离编排复现：模拟 SQL dump 保留附件引用，同时模拟快照后的普通删除；真实执行媒体复制、归档与 `validate_backup()`：

```text
Backup marked valid=True
SQL references attachment=True
Archive includes attachment=False
```

这里确认的是一致性机制缺失，并非已观察到生产数据损坏。归档校验能确认已有成员的结构/完整性，不能确认快照数据库引用的媒体全部存在。

建议：建立数据库与文件共同的一致性边界。短期可在备份关键阶段停写并推迟物理删文件；更长期可使用不可变媒体、版本化存储或协调快照。区分“归档校验通过”和“业务恢复验证通过”。

### S05 · P2 · 浏览器会话失效后不会自动回到登录状态

证据：[api.ts:189](/Users/zhang/Documents/ChatGPT/ITAM/frontend/src/api.ts:189)、[auth_security.py:131](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/auth_security.py:131)、[useApiClient.ts:76](/Users/zhang/Documents/ChatGPT/ITAM/frontend/src/composables/useApiClient.ts:76)。

后端无 Bearer 请求的未认证响应为 HTTP 403；前端通用请求只在 401 时执行 `onUnauthorized()`。403 分支直接抛出“无权限”错误。初次 `/auth/me/` 探测专门处理了 403，但已登录期间的普通业务请求没有同等处理。

分别验证：真实 DRF 资产列表在匿名请求下返回 `403 / not_authenticated`；前端 fetch 复现同类响应时 `onUnauthorized` 调用次数为 0。

影响：会话到期后界面仍认为已登录，后续操作反复出现无权限提示；旧页面数据可能继续显示，用户难以理解实际状态。不是后端鉴权失效，后端已拒绝请求。

建议：区分未认证、权限不足和 CSRF 失败，统一响应错误码；未认证时清除会话状态并进入登录流程。不要把所有 403 一律当作注销。

### B02 · P1 · 机房跨数据中心迁移破坏备件库存归属

证据：[physical_location.py:393](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/physical_location.py:393)、[views.py:1755](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/views.py:1755)。

### B03 · P1 · 备件位置筛选导致库存重复累计

证据：[views.py:2358](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/views.py:2358)、[views.py:2408](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/views.py:2408)、[serializers.py:1622](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/serializers.py:1622)。

查询先用库存反向关联求和，再通过另一个反向关联 JOIN 筛选数据中心。多个匹配位置会复制聚合行，最后的 `distinct()` 不能修复已经重复累计的 Sum。

隔离复现：一个中心的两个库存位置各 5 件，实际总量 10、安全库存 15；中心筛选后的 `total_quantity=20`、`is_low_stock=False`。

影响：列表库存和低库存判断错误。备件导出通过同一 ViewSet 生成查询，也受到影响。无位置筛选的告警可能仍正确，导致不同页面口径冲突。

建议：先定义“筛选地点的库存”还是“符合地点条件的备件全局库存”的口径，再用 Exists 或独立聚合子查询实现。不要用 Sum(distinct quantity) 修补，否则两个真实 5 件余额又会被合并成一个。

### B04 · P2 · 全资产盘点的机柜覆盖统计固定为零

建议：根据任务 scope 计算统计范围，明确使用任务创建时冻结范围还是当前设施范围。验收应覆盖全部资产、数据中心和机房三种任务。

## 5. 架构风险

### 5.1 保持单体，按业务域形成清晰边界

`views.py` 有 5,807 行，`serializers.py` 有 3,739 行，`services.py` 有 1,599 行；前端 `App.vue` 有 2,428 行，`useAssets.ts` 有 3,089 行。认证、组织、库存、盘点、报表和维护等不同变化原因仍聚集在少数文件。这是可能的 Divergent Change 判断，不是“文件超过某个行数就一定有 bug”。

现有 `physical_location`、`organization_access`、`reporting` 和维护模块已经体现了领域边界，应沿着这些方向继续拆分。推荐先形成 identity、asset lifecycle、facilities、stock、inventory、maintenance、licensing、reporting、operations 等模块，保证每个业务写入通过一个清晰的服务入口维护事务、权限和审计。

暂不建议为了成熟度而拆成微服务。当前暴露的问题更需要统一事务与领域约束，过早引入分布式一致性会增加负担。

### 5.2 在线恢复缺少普通业务停写屏障

[backups.py:1357](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/backups.py:1357) 先切换媒体，再导入数据库。维护操作锁不阻断普通业务请求，恢复阶段可能继续收到读写。这是代码确认的竞态风险，本次未执行生产恢复来复现丢写。

应将恢复作为受控维护作业：阻止新写入、等待已有请求排空、执行安全备份和恢复、验证数据库及媒体、使凭证/会话策略生效，再开放请求。数据库导入与文件切换无法被一个 Django 事务原子覆盖，要有明确的失败和回滚状态。

### 5.3 长任务依赖 HTTP worker 生存期

备份、恢复和报表为同步 HTTP 操作，备份数据库子进程调用未配置超时；部署的 Gunicorn [install.sh:949](/Users/zhang/Documents/ChatGPT/ITAM/deploy/install.sh:949) 配置 `--timeout 120`。大备份或恢复可能超过 worker 超时，存在 worker 被终止而作业状态不完整的风险，本次没有测量实际生产阈值。

建议引入持久作业记录、后台执行、进度查询、失败恢复和独立超时。先用适合部署规模的简单 worker 即可，不必立即引入复杂平台。作业必须可观察，特别是恢复和批量导入。

### 5.4 当前权限是全局功能权限

后续阶段已新增独立的数据中心读写范围、待归属授权与全局库存指标授权，核心资源、附件、中心内报表、导出及逐条批量业务遵守同一范围。授权撤销等待在途请求及流式下载完成。本批追加独立资产归属部门及中心/部门交集授权，保护人员选择、共享机柜占用及完整盘点投影。旧数据只读预览不自动回填。本批已适配局部资产导入、共享型号导出与安全资产时间线；新审计冻结当时范围，旧证据不足的明细明确隐藏，不修改历史日志。本批完成基础及附加规则的完整条件并集，读写组合不交叉扩张，盘点观察冻结原部门，资产联合归属/位置变更在锁内检查两端；并发读取使用一致快照避免设施改挂后的混合响应。公司级隔离仍未完成。当前规则见 `docs/DATA-SCOPE.zh-CN.md`；以下保留审查基线说明。

[organization_access/__init__.py:91](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/organization_access/__init__.py:91) 定义四个固定角色，`can()` 判断能力字符串。没有部门、数据中心、公司、资产负责人等行级数据范围。

这是设计边界，不应在没有数据隔离要求时冒充越权 bug。但多部门使用时，角色相同的人会获得全局数据范围，无法实现“只能维护自己的中心”。建议功能能力与数据范围分别建模，并由列表、详情、导出、批量操作和关联选择统一使用。

### 5.5 行锁不能防止旧表单覆盖新数据

第三批落实资产详情版本比较，以及备件流水、维修用件的幂等提交；第四批覆盖 15 类主数据及字段集成员替换；阶段 2A 补齐账号、本人资料、系统/品牌/LDAP 配置、故障、维修、盘点与附件，账号批量启停采用逐条版本。协议范围和兼容变化见 `docs/WRITE-CONSISTENCY.zh-CN.md`。以下保留基线问题的说明。

[useAssets.ts:2199](/Users/zhang/Documents/ChatGPT/ITAM/frontend/src/composables/useAssets.ts:2199) 编辑时提交较完整的资产和配置；[serializers.py:2987](/Users/zhang/Documents/ChatGPT/ITAM/backend/assets/serializers.py:2987) 会重新读取并锁行，但没有对用户打开表单时的版本进行冲突校验。

两个管理员先后保存旧表单时，后保存者可能用旧字段覆盖前者刚改的内容。行锁能让数据库写入串行，不能发现表单已过期。这是由写入协议推导的架构风险，尚未进行双浏览器端到端复现。

建议增加 revision/ETag 或等价条件更新；过期写入返回明确冲突。同时明确备件操作、维修用料等非幂等写入在网络重试时的请求幂等策略。

### 5.6 验证能力尚未覆盖主要风险边界

当前 94 个后端测试和 3 个前端测试均通过，但此次仍复现多个关键缺陷。不能用测试数量推导覆盖率。本次仓库文件检查未发现 CI 工作流；前端 package scripts 未提供 test 入口，后端依赖采用版本范围而无锁定文件。

建议自动执行已有测试与构建，并补充实际 MariaDB 的事务/并发验证、Session/PAT/Admin 认证策略一致性验证、跨域位置迁移、筛选聚合及备份恢复演练。前端优先增加登录过期和关键业务闭环的端到端检查，避免大量只复述实现的浅层测试。

### 6.1 软件超授权告警与录入约束相互矛盾

## 7. 整改顺序与验收标准

四批修复后的后续实施顺序以 [后续分阶段计划](NEXT-STAGES.zh-CN.md) 为准：工程基线、数据范围权限、写入与后台作业、业务历史、发现与对账、成熟 ITAM 能力。以下保留原审查时的三阶段建议。

### 第一阶段：保证当前功能可信

第一批已修复 S01、S04、B01、B02、B03，补 S02 实际入口回归，并同步修复 S03；落地 CLI 备份恢复及维护屏障。第二批已完成 S05、S06、B04、B05 的补充收尾，详见报告开头的当前状态。

本阶段验收：所有认证入口遵守同一安全策略；合法空白历史数据不使通知崩溃；位置变更不会遗留不可操作库存；筛选前后库存量口径明确且不会因 JOIN 放大；备份包含数据库引用的所有应备媒体，备份及恢复期间动态请求被阻断，失败恢复在验收完成前持续维护。

### 第二阶段：补架构边界与历史一致性

按业务域收拢写入入口和审计；补旧表单版本冲突检测、数据范围授权、历史位置快照、资产软删除/报废留存；将长任务移出 HTTP worker。建立自动验证入口和 MariaDB 集成验证。

验收要求：一个状态变更只通过明确服务维护；同一实体各写入入口共用不变量；多部门范围对列表/详情/导出/批量操作一致生效；历史事实不受主数据改名或迁移影响；任务失败能够定位阶段并恢复。

### 第三阶段：按定位建设成熟 ITAM 能力

先确定优先服务基础设施机房运营，还是全企业终端与软件资产管理。前者优先设备发现、位置/网络模型、CMDB关系、合同及维修历史；后者优先 HR/ERP 对接、领用审批/确认、终端采集、软件授权对账和离职回收。

每项能力都应同时定义事实来源、身份匹配、审批/纠错职责、事件历史、统计口径和失败恢复，避免只增加录入表单。

本次不建议推翻技术栈，也不建议直接重写全系统。先消除已复现的数据与安全缺陷，再在现有单体中建立更完整的领域边界，收益更明确。
