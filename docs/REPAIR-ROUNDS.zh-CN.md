# 多轮维修历史

阶段 3A 保留故障和维修 API 的路径，在一个故障下保存多个维修轮次。`FaultEvent.repair` 和故障响应的 `repair` 始终是轮次编号最大的记录，`repair_round_count` 返回轮次数量。告警仍按未关闭故障生成，历史完成轮次不会重复触发故障告警。

## 轮次和证据

首次创建维修形成第一轮；未填写维修时首次用件会建立空白第一轮，随后创建维修会填写该轮，沿用 ID 和用件关联。重开当前已完成轮次形成下一轮，返回新的维修 ID；服务商、费用、备注和维修时间为空。上一轮保留原完成时间，不能通过重开覆盖或复制费用。

`round_number`、`previous_round`、`origin`、建轮及完成人员由服务器维护。名称快照保留执行时身份（最多 150 字符），账号后续删除不会抹去名称。来源分别为正式记录 `recorded`、首次用件建轮 `usage_started`、迁移的历史记录 `legacy`。未知费用仍为空，零费用仍为零。

完成和重开在一个事务内同步故障关闭状态、解决时间、资产维修前状态及审计。普通编辑仍要求 `If-Match`。重复重开旧轮次返回 HTTP 409 / `repair_round_conflict`；历史轮次不能改变当前故障状态。任何一轮时间都不能早于故障，后续轮次不能早于前轮完成；仍允许先维修后补报障。

已完成轮次持续只读，保留其用件和专属附件。进行中轮次可以维护附件；完成、领料和附件写入共用故障父锁，业务事务及文件回调结束前持维护访问锁。已归档资产的轮次和附件仍按原范围授权可读，禁止修改。

## 查询和兼容

- `GET /api/v1/repair-records/?fault={id}&ordering=-round_number`：分页轮次历史，各条响应含 `is_current`。
- `POST /api/v1/repair-records/{id}/reopen/`：从当前完成轮次建立空白下一轮，成功仍为 HTTP 200。
- `GET /api/v1/fault-events/{id}/part-usages/?repair={round_id}`：所选轮次用件。`repair=legacy` 查询未确认归属的历史用件，省略参数查询全部。
- 用件 POST 增加可选 `repair_id`。传入 ID 或明确空值时，与事务内当前轮次比较；不一致返回 HTTP 409 / `repair_round_conflict`。旧客户端省略时使用提交当时的当前轮次。既有幂等键重放原结果，不重复扣库，也不把旧用件移到新轮次。
- 维修导出保留第一张表的当前轮次字段，追加“维修轮次”表，列出过滤后的故障全部轮次、费用、时间及人员。两张表共同遵守原范围、过滤条件及数量限制，未知费用不补零。

前端可选择轮次查看维修结果、用件和附件；用件面板保留所选轮次、未确认历史和全部三种查询。重开确认说明会新建轮次。旧请求迟到后不关闭或覆盖新打开的编辑草稿，写入失败不自动重试。

## 升级与历史边界

升级使用正常 `manage.py migrate --noinput` 应用迁移 0015。按既有升级流程停止 Web、worker 和摘要定时器，完成数据库与前端同版本更新后启动。单机维护及备份恢复继续按[部署运行手册](DEPLOYMENT.zh-CN.md)执行；旧版本备份需要匹配其程序和迁移版本，不能直接当作跨版本回退工具。

既有维修 ID、费用、时间、版本号、故障及附件关系保留，标为历史第一轮；不推测曾经被重开抹去的轮次，也不推测建轮和完成人员。旧用件均保留原库存流水和幂等事实，轮次标为 `legacy_unassigned`、维修关联为空；即使同一故障有现存维修，也不能可靠证明其属于该轮。本批不提供自动归属或自动补造工具。

存在轮次的故障禁止直接删除。第一轮仅在未完成且没有前轮、用件或附件时允许删除；后续轮次持续保留。管理员显式系统重置仍按依赖顺序删除完整业务数据，属于既有破坏性操作。

本批仅完成维修历史；独立合同、采购单据、审批和完整成本分析继续按阶段 3B、3C 及阶段 5 实施。
