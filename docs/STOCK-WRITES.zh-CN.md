# 库存领域写入

库存余额只能由入库、出库、报废、调拨、盘点调整或维修领料改变。备件目录、地点余额、库存流水与维修用件分别保留其现有含义；本批不改变计量单位、全局库存统计或历史流水。

## 写入入口

`backend/assets/stock.py` 统一维护库存操作规则、当前权限、余额锁、事实写入和审计。视图接收请求并调用字段序列化器，序列化器将业务规则交给该模块。

| 入口 | 负责的行为 |
| --- | --- |
| `record_stock_transaction` | 普通库存操作，重试前授权，幂等结果与余额、流水、审计同事务提交 |
| `record_repair_part_usage` | 维修领料，当前故障及库存授权，幂等提交，内部库存扣减或厂商供件事实 |
| `create_spare_part_with_stock` | 创建备件、可选初始余额、初始流水及两类审计一起提交或回滚 |

上述 HTTP 提交入口保留原路径、请求字段、成功结构和幂等键规则。维修用件的重放也必须拥有当前 `faults.manage`；内部领料还须拥有当前 `spares.manage`，同时满足故障/资产及所选库存的数据范围。撤销库存功能能力后，同键重放返回 403，不能凭旧成功结果绕过当前权限。允许保留的历史读取仍按已有读取权限执行。

原 `assets.services` 的库存函数只做兼容导出，底层实现和审计已移至库存模块；调用方不得再重复写审计。兼容的底层函数用于服务器内部组合，不单独提供幂等重放。HTTP 调用使用上表提交入口；以后接入 worker 时，仍须在准入层持有维护与账号授权访问锁，使用统一幂等提交语义，并覆盖事务及提交后的回调。不能把底层兼容函数当作已具备后台作业准入的入口。

## 事务与锁

普通库存操作按备件 → 数据中心 → 机房 → 余额取得锁。一次调拨涉及多个数据中心或机房时，分别按主键排序，并在锁内重查启用状态、中心/机房匹配及可用余额。无机房余额的创建也由备件与数据中心锁协调。失败不留下新零余额、半次调拨或成功审计。

内部维修领料先取得备件和库存地点、余额的锁，再按故障 → 维修 → 资产检查当前生命周期和资产范围，最后写入扣库流水与领料事实。这避免先持有资产、再等待设施变更已持有的地点锁。领料与出库竞争同一余额时，锁内判断库存，不允许同时超额扣减。厂商提供的用件不改变内部库存。

故障、维修已完成，或资产已归档/报废时，仍阻止新领料。正常成功结果继续保存部件、计量单位、库存地点及操作者快照；既有记录和流水不回写。

审计属于业务事务的一部分。余额、流水、维修用件或初始备件写入成功，但审计存储失败时，整个操作回滚，幂等结果也不能提前保留。修复存储后，原逻辑操作可以使用原键重新提交。

## 前端与兼容

`useSpareParts` 保留页面原接口，目录编辑、列表和读取行为继续由其组织；库存操作表单、地点预填、操作校验反馈和保存交给 `useSpareStockOperations`。保存后的目录刷新失败仍提示业务已经提交，不自动再做一次写入。

备件目录编辑保留打开时的版本副本，列表对象后来变化不会给旧表单换上新修订号。冲突保留输入。库存操作遇到维护或网络错误不自动重试，保留表单和未确认操作身份；手工重试原内容复用键，成功后的下一次操作使用新键。

本批无需新增迁移。已有环境仍须先完成前面批次的迁移及外部客户端协议升级；开发业务库不自动迁移。维护、备份和恢复继续沿用现有单机多 worker 协调与服务器 CLI。
